# 행동 스펙 (Agent Behavior)

게이트는 **결과**를 잰다. `evidence.ts` 는 카드가 무엇을 관찰했는지 묻고, ship 게이트는
리뷰가 붙었는지 묻는다. 둘 다 끝난 뒤의 질문이다.

그런데 에이전트가 카드 하나에서 내리는 결정은 수백 개이고, 그 대부분은 어떤 게이트도
보지 않는다 — 초록을 믿을지, 리뷰를 누가 할지, 못 한 것을 말할지, 되돌리기가 실패한
스크립트를 계속 돌릴지. 그리고 그것들은 **반복해서 같은 방식으로** 어긋난다.

[Agent Behavior](https://agentbehavior.dev)는 그 반복되는 처신을 파일 하나에 적어
두는 공개 형식이다. 이 하네스는 그 형식을 그대로 쓴다.

## 어디에 있나

    .agents/behaviors/
    └── <name>/
        ├── BEHAVIOR.md     # 필수: YAML frontmatter + Markdown 본문
        └── references/     # 선택: 근거·사례·배경

디렉터리 이름이 스펙의 안정된 식별자이고 `name:` 과 같아야 한다.

## 지금 담긴 것

| 이름 | 무엇을 못박는가 |
| --- | --- |
| `tests-that-bite` | 초록을 근거로 쓰기 전에 검사가 무는지 확인한다. 판정은 종료 코드로 한다 |
| `evidence-before-done` | done 은 주장이 아니라 측정이다. 증거의 수치는 읽는 것이지 적는 것이 아니다 |
| `independent-verification` | 자기 작업을 자기가 승인하지 않는다. 승인은 sha 에 묶이고 커밋이 붙으면 만료된다 |
| `honest-reporting` | 실제로 일어난 것만 보고한다. 확정하지 못한 원인은 확정하지 못했다고 적는다 |
| `change-provenance` | 커밋은 출처를 밝히고, 병렬로 일할 때는 작업 공간을 나누며, 기준 브랜치는 리뷰를 거친 변경만 받는다 |
| `product-engineer-mindset` | 단순 태스크 수행자가 아닌 문제 해결의 주체로서 행동한다. 사용자 도메인을 이해하고, 근거 있는 의견을 제시하며, 데이터와 목표로 판단한다 |
| `code-driven-knowledge-ssot` | 코드를 유일한 근거로 삼아 2-Tier(raw ➔ knowledge) 지식을 유지하고, 식별자 무결성을 보존하며 스펙 주도 개발을 수행한다 |
| `spec-driven-service-creation` | Vibe Coding을 금지하고, 기계 판독 가능한 사양(SPEC.md/Data Contract/AC)을 먼저 동결한 뒤 TDD 루프와 3-Tier 다층 심층 검증을 거쳐 서비스를 구축한다 |

**대부분은 새 규칙이 아니다** — `docs/harness-gates.md` 와 각 ADR 에 흩어져 있던
처신을, 트레이스를 읽고 eval 을 설계하는 사람이 한 곳에서 볼 수 있게 옮긴 것이다.
규칙의 강제는 여전히 게이트가 한다.

**세 곳은 새로 적은 것이다.** `tests-that-bite` 의 변이 절차(초록을 근거로 쓰기 전에
생산 코드를 훼손해 빨강을 확인한다)는 기존 규칙 어디에도 문장으로 없었고, 
`evidence-before-done` 의 "증거의 수치는 명령에서 읽는다", `change-provenance` 의
"커밋에 출처 표식을 남긴다" 도 마찬가지다. 셋 다 **제안된 규칙**이며 게이트가
강제하지 않고, 각 스펙이 그 사실을 밝힌다.

## 검사

    node scripts/loop/behavior-spec.ts list    # 발견된 스펙
    node scripts/loop/behavior-spec.ts check   # 규격 위반이면 종료 코드 1

`health.sh` 의 fail-closed 구간에서 돌기 때문에 건너뛸 수 없다.

**보장의 세기는 셸마다 다르다.** POSIX 쪽은 검사가 `health.sh` 를 **실제로 실행해**
깨진 스펙에서 그 단계가 실패하는 것을 확인한다. PowerShell 쪽은 이 기계에 pwsh 가
없어 **호출 줄의 모양만** 본다 — 그 줄을 조건으로 감싸 무력화하는 것을 잡지 못한다.
같은 한계가 `ci.yml` 에도 있다. 감추지 않고 적어 둔다. 스펙이 하나도 없는
프로젝트는 통과한다 — 없는 것은 위반이 아니다.

검사하는 것은 규격이 MUST 로 정한 것뿐이다: frontmatter 존재, `name` 의 모양과
디렉터리 일치, `description` 의 존재와 길이, 본문 존재. **모르는 frontmatter 필드는
무시한다** — 상류가 필드를 늘릴 때 이쪽만 깨지지 않도록 규격이 그렇게 정했다.

## 왜 상류 CLI 를 쓰지 않나

`braintrustdata/agentbehavior` 의 `agentbehavior` 패키지는 npm 에 올라와 있지 않다
(2026-08 확인, 404). 그리고 `scripts/loop/` 의 스크립트는 생성된 프로젝트에서
**설치 없이** 돌아야 해서 이 디렉터리 전체가 `node:` 빌트인만 쓴다. 그래서 규격의
discovery·validation 쪽만 직접 구현했다. 패키지가 올라오면 바꾼다.

같은 이유로 YAML 파서도 쓰지 않는다. **그래서 이것은 규격 검증기가 아니라 저장소
위생 검사기다** — 그 차이를 감추지 않는다. 값의 YAML 유효성을 직접 판정하려다 다섯
라운드에 걸쳐 양쪽으로 틀렸다: 유효한 `yes`·`!!str`·anchor·여러 줄 값을 막고, 깨진
`[unterminated`·`"\q"`·`[one] trailing` 을 통과시켰다. 손으로 만든 부분문법은 상류
파서와 같아질 수 없다. 그래서 그 주장을 접었다.

지금 검사하는 것은 여섯이고, 전부 YAML 파싱 없이 확실히 판정된다:

- `.agents/behaviors/<dir>/BEHAVIOR.md` 가 **정식 이름으로** 있는가
- 디렉터리 이름이 규격의 모양(소문자·숫자·하이픈)과 길이 상한을 지키는가
- 디렉터리가 끊어진 링크이거나, 링크이거나, 읽을 수 없지 않은가
- 파일이 `name: <dir>` 를 **그 디렉터리 이름 그대로** 선언하는가
- 비어 있지 않은 `description:` 줄이 있는가
- frontmatter 뒤에 **본문**이 있는가

이 여섯은 실제로 일어나는 사고를 잡는다: 디렉터리 이름만 바꾸기, 파일 지우기, 내용
비우기, 링크로 대체하기. **값의 YAML 유효성은 상류 CLI 의 일이고**, 그것이 npm 에
올라오면 이 파일을 버린다.

## 새 스펙을 넣을 때

행동이 이 조건에 맞을 때만 넣는다: 여러 트레이스에 **반복**되고, 틀리면 **영향이
크고**, 이 하네스가 어떤 하네스인지 **규정하고**, 적어 두지 않으면 **사람마다 다르게**
할 만하고, 흩어진 문서를 다 읽어야 알 수 있는 것. 도구 문법이나 일회성 절차는 넣지
않는다.

권장 축은 여섯이다 — Intent(왜·언제), Evidence(결정 전에 무엇을 확인하나),
Decision(무엇을 판단하나), Execution(결정 뒤 무엇을 하나), Recovery(첫 경로가
실패하면), Failure modes(무엇을 막으려는 스펙인가). 자명하면 합치거나 빼도 된다.

넣은 뒤 `node scripts/loop/behavior-spec.ts check` 로 확인한다.
`tests/behavior-spec.test.ts` 가 배포되는 스펙 전부를 검사하고 **이름 집합까지 센다** —
하나를 지우거나 오타를 내면 실패한다. 세지 않던 판에서는 스펙 하나를 지워도 전부
초록이었다. 루트 사본은 `template/` 에서 다시 만들어진다 — `--refresh-generated` 가 덮어쓰므로 손으로 고치지 않는다.
